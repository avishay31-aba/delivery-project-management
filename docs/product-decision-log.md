# Product Decision Log

This log captures durable product and architecture decisions supported by current repository documentation and implementation context. It is not a duplicate rule catalog. Authoritative behavior remains in `AGENTS.md`, `docs/architecture-handbook.md`, `docs/v1.2-standing-product-rules.md`, the ECM/BOM, BOS, PDS, ADRs, roadmap, and release notes.

If rationale is not recoverable from repository documentation, this log records it as not currently documented rather than guessing.

| Date / Phase | Decision | Rationale | Authoritative Rule / Specification | Superseded Rule / Decision |
| --- | --- | --- | --- | --- |
| V1/V1.2 | Delivery ERP is organized as `Console -> Workspace -> Business Object`, not by job title. | Repository documents explain that roles determine permissions while workspaces and Business Objects determine ownership. | `docs/architecture-handbook.md`, `docs/enterprise-capability-model/delivery-erp-ecm-v1.md`, `docs/business-object-model/delivery-erp-bom-v1.md` | None documented. |
| V1/V1.2 | Sales owns Customer/Account and Opportunity. Delivery owns Project, System, Tenant, Warranty, Allocation, operational renewal, and requirement fulfillment read models. Admin owns Activity/Audit and future governance objects. | Ownership boundaries prevent cross-domain status/rule drift and preserve single source of truth. | ECM, BOM, and BOS files under `docs/business-objects/` | None documented. |
| V1/V1.2 | Requirement definitions are Sales-originated through Opportunity/TenantRequirement; Requirement Coverage is a Delivery-owned validation/read-model surface, not a Business Object Workspace. | Requirement Coverage validates and aggregates facts owned by Opportunity, Project, System, Tenant, and Allocation without owning editable lifecycle or master data. | `docs/business-object-model/delivery-erp-bom-v1.md`, `docs/v1.2-standing-product-rules.md`, `docs/business-objects/bos-opportunity.md`, `docs/business-objects/bos-project.md` | None documented. |
| V1/V1.2 | Systems Workspace owns Allocated, Production, and Reused Internal Systems as views/tabs of the System Business Object rather than separate Business Objects. | Repository documentation treats System as one Delivery-owned infrastructure resource concept with multiple operational views. | `docs/architecture-handbook.md`, `docs/business-object-model/delivery-erp-bom-v1.md`, `docs/business-objects/bos-system.md`, `docs/product-design/pds-systems-workspace.md` | Earlier navigation may have exposed system subsets as separate visible items; current guidance recommends tabs/views. |
| V1/V1.2 | Approved business forms and operational workflows are product assets and must not be redesigned as a side effect of architecture work. | The architecture is intended to improve maintainability, ownership, consistency, and extensibility while preserving proven user workflows. | `docs/architecture-handbook.md`, PDS files under `docs/product-design/` | None documented. |
| V1/V1.2 | Equivalent product behavior must reuse shared infrastructure and shared components rather than local approximations. | Shared implementations keep equivalent statuses, links, selectors, dashboard controls, pagination, read-only presentation, and interactions consistent across the application. | `AGENTS.md`, `docs/architecture-handbook.md`, `docs/v1.2-standing-product-rules.md`, BOM shared component matrix | None documented. |
| V1/V1.2 | Business rules belong in Business Object domains, services, authoritative read models, and store transactions, not page-only UI code. | Prevents duplicated derivations, stale state, and inconsistent behavior between forms, dashboards, export, history, reload, and navigation. | `AGENTS.md`, `docs/architecture-handbook.md`, `docs/v1.2-standing-product-rules.md`, BOS/PDS files | None documented. |
| V1/V1.2 | Each explicit Save/Apply action is the commit boundary for its owned scope; independently owned child-object saves commit independently. | The architecture requires drafts to remain local and committed values to update authoritative stores/read models immediately. | `docs/architecture-handbook.md`, `docs/v1.2-standing-product-rules.md` | None documented. |
| V1/V1.2 | Every Business Object participates in the shared Audit Trail framework, with events created by domain/store transactions rather than React pages. | Audit records are immutable chronological business records; page-level emission would duplicate or bypass transaction authority. | `docs/architecture-handbook.md`, ECM/BOM, BOS files | None documented. |
| V1/V1.2 | Every displayed Business Object ID must use the shared Business ID/reference presenter where a supported route exists. | Shared presenters own route-aware fallback behavior and prevent duplicated routing logic or broken links. | `docs/architecture-handbook.md`, `docs/v1.2-standing-product-rules.md`, BOM/PDS files | Local anchor/routing implementations are superseded where a shared presenter exists. |
| V1.2 Final QA | V1.2 dashboard and table behavior uses shared controls for fixed action/indicator columns, pagination, filters/search, frozen columns, preferences, and CSV export. | The repository documents this as a cross-application invariant; detailed rationale is not currently documented beyond consistency and shared ownership. | `docs/v1.2-standing-product-rules.md`, `docs/architecture-handbook.md` | Older/local dashboard behavior is superseded where it conflicts with the shared `DataDashboard` standard. |
| V1.2 Final QA | Only Update/New and Actions are permanently fixed Dashboard columns; Creation Date is ordinary, Freeze Through starts with eligible business columns, and grouping preserves configured order. | Permanent UI columns are framework controls while Creation Date is object data whose placement differs by approved object model. | `docs/v1.2-standing-product-rules.md`, `docs/architecture-handbook.md` | The former Creation-Date-controlled column/freeze rule is superseded. |
| V1.2 Final QA | Tenant Dashboard PID and Requirement ID are relationship-aware multi-value cells over all active Project-Tenant relationships. | Multiple simultaneous active commercial relationships are legitimate and must not be collapsed through artificial precedence. | `docs/v1.2-standing-product-rules.md`, `docs/business-objects/bos-tenant.md` | Separate POC PID/Delivery PID Dashboard columns and single-current-Project assumptions are superseded. |
| V1.2 Final QA | An eligible POC Tenant on a Production System may convert to Customer only through fulfilled Delivery/Renewal Upsell Change Request workflow. | Retaining the successful POC Tenant preserves operational continuity and historical truth while adding later commercial relationships. | Tenant, Opportunity, Project and System BOS; V1.2 standing rules | Unqualified post-creation Tenant Type immutability is superseded only for this controlled transition. |
| V1.2 Final QA | Infrastructure has no user-facing Delete action or Deleted Items dashboard; `Obsolete` remains an independent operational status. | Rationale for superseding Infrastructure Delete/Restore is not currently documented in detail. Current rules state the supersession and retention behavior. | `docs/v1.2-standing-product-rules.md`, `docs/architecture-handbook.md` | Infrastructure Item Delete/Restore workflow was superseded during V1.2 Final QA. |
| V1/V1.2 | Project Delete is a recoverable lifecycle transition that preserves PID, relationships, history, activity, and dashboard visibility. | Repository documentation treats deletion as business lifecycle/history, not physical removal. | `docs/architecture-handbook.md`, `docs/v1.2-standing-product-rules.md`, `docs/business-objects/bos-project.md` | None documented. |
| V1.2 Final QA | Tenant Warranty Status is derived from committed Warranty Business Objects by WarrantyCollection and is presented only according to approved aggregate labels. | Draft warranty rows must not affect shared read models; pages must not independently compute the aggregate. | `docs/architecture-handbook.md`, `docs/v1.2-standing-product-rules.md`, `docs/business-objects/bos-tenant.md` | Any page-level Tenant warranty aggregate logic is superseded. |
| V1.2 Final QA | Tenant Type is determined at creation and is immutable after creation or hosting moves. | Current repository rationale is not documented beyond ownership and lifecycle consistency. | `docs/v1.2-standing-product-rules.md`, `docs/business-objects/bos-tenant.md` | None documented. |
| V1.2 Final QA | Tenant and Project geography derive from Customer/Opportunity context; Time Zone derives from Country/State; Time Group resolves only through active Time Group Settings. Region is not a fallback. | Prevents stale or ambiguous geography/time-group derivations across dependent Business Objects. | `docs/v1.2-standing-product-rules.md`, `docs/business-objects/bos-customer-account.md`, `docs/business-objects/bos-project.md`, `docs/business-objects/bos-tenant.md` | Region-based fallback behavior is superseded. |
| V1.2 Final QA | System Time Group represents external Customer/POC working-hours governance for maintenance; only active Customer/POC Tenants can govern it. | Internal tenants do not represent external customer working hours. Explicit Change selection and veteran-tenant precedence provide deterministic governance. | `docs/v1.2-standing-product-rules.md`, `docs/business-objects/bos-system.md` | Project Time Group, Project age, Region, Internal Tenants, and non-governing Tenants are rejected as fallbacks. |
| V1.2 Final QA | Reused Internal System MID input is digits only; display is `M<digits>`, and blank MID remains blank. | Detailed rationale is not currently documented. | `docs/v1.2-standing-product-rules.md` | Any display-only generation or user-entered `M` prefix behavior is superseded. |
| V1.2 Final QA | Recurring Infrastructure Maintenance Task behavior is keyed by recurrence identity fields, not description, task name, dates alone, or visual similarity. | Stable recurrence identity preserves occurrence history, overrides, and series edits/cancellation semantics. | `docs/v1.2-standing-product-rules.md` | Inferred recurrence membership is superseded. |
| V1.2 | V1.2 is closed as the final frontend-only/browser-persisted milestone. | V1.2 is intended for validation, QA, demonstration, and release handoff, not final production security or deployment architecture. | `docs/product-roadmap.md`, `docs/releases/v1.2-release-notes.md`, `docs/architecture-handbook.md`, `docs/architecture-decisions/adr-0001-version-2-backend-boundary.md` | Earlier MVP/future backend assumptions in root-level design docs are historical rather than current V1.2 authority. |
| V2.0 | Security-sensitive capabilities require a trusted backend boundary before implementation. | Browser storage and client-side code are inspectable/modifiable; password hashes, sessions, authorization, upgrade credentials, and admin write operations require trusted infrastructure. | `docs/architecture-decisions/adr-0001-version-2-backend-boundary.md`, `docs/product-roadmap.md`, `docs/release-management-backlog.md`, `docs/architecture-handbook.md` | Frontend-only login, local password storage, browser-stored password hashes, fake roles/permissions, browser release publishing, and incomplete Update Agent behavior are excluded from V1.2. |
| Future release management | V1 release deployment remains manual DevOps responsibility; release publishing must not be added to the browser app. | Deployment credentials and publishing require secured backend ownership, server-side authorization, validation, health checks, immutable release history, and rollback support. | `docs/release-management-backlog.md`, `docs/architecture-decisions/adr-0001-version-2-backend-boundary.md` | Placeholder Publish buttons, browser deployment credentials, and frontend-only release-management controls are excluded. |
