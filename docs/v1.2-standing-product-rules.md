# Delivery ERP V1.2 standing product rules

## Purpose and authority

This document records the **current approved cross-application V1.2 behavior**. It is an invariant catalog, not a defect or decision history. Apply it together with the [Architecture Handbook](architecture-handbook.md), which remains authoritative for architecture, ownership, and implementation methodology. More-specific Business Object specifications remain authoritative within their stated scope, but must not silently override a generic invariant.

If a requested change conflicts with this document, stop and report the conflict before implementation.

## A. Business identity and navigation

- **Any displayed Business/Object ID must use the shared navigable Business ID/reference presenter whenever a valid target object and supported route exist.** This applies to forms, headers, dashboards, tables, history and configuration history, relationship summaries, candidate dialogs, and read-only presentations.
- Use `BusinessObjectLink`, `BusinessIdLink`, and the Business Reference Resolver. Do not reproduce routing or fallback behavior locally.
- Empty IDs, technical keys, invalid/stale references, and historical snapshots without a valid target use the shared safe fallback rather than a broken link.
- Export and persistence retain plain business-ID text; React link markup never becomes domain data.
- Reused Internal System MID input is digits only. Users do not enter the `M`; display is `M<digits>`. A blank MID remains blank and is not generated merely for display.

## B. Shared and equivalent UI behavior

- Equivalent behavior must use the approved shared implementation and appear and behave identically across Business Objects.
- This includes workspace navigation, Product sub-tabs, dashboard controls, pagination, Business ID links, selectors, action controls, status/indicator presentation, deletion/history presentation where approved, and read-only fields.
- Do not create an object-specific visual approximation when a shared pattern exists. Extend the shared pattern safely when a genuinely generic capability is missing.

## C. Read-only presentation

- Read-only and system-derived values use the shared contour-free read-only presentation.
- Do not display a non-editable value as a disabled editable control unless the control has an approved inactive-state purpose (for example, showing the locked recurrence definition during occurrence editing).
- View mode must not expose accidental editing affordances. Domain/store commit boundaries must enforce the same effective editability as the UI.

## D. Controlled dashboard columns

- `New/Updated` is the first/leftmost row indicator. It is fixed and cannot be hidden or moved.
- `Actions` is a fixed UI-control column. It cannot be hidden, moved, saved as business data, or exported.
- `Labels` follows the shared fixed-column behavior.
- `New/Updated`, `Actions`, and `Labels` have no column menu.
- The configurable column-menu sequence begins at `Creation Date` and continues to the right. Creation Date retains its fixed location.
- `Freeze Through` choices begin after Creation Date and expose only the next five effective visible columns.
- Freeze choices derive dynamically from the effective saved-view column order. The shared `DataDashboard` owns frozen positioning and boundary behavior.

## E. Pagination, search, filters, and CSV

- Paginated dashboards and history/form tables use the common `DataDashboard` or `RecordHistorySection` behavior. Equivalent pagination must not be reimplemented per page.
- Records-per-page choices are `10`, `20`, `25`, `50`, `100`, and `All`; the system default is 10 unless an approved logical table default applies. User defaults belong to presentation preferences, not Business Objects.
- Search/Filter updates results immediately. When text is present, the shared inline `×` clears the complete query and resets pagination; it is absent when the query is empty.
- Date filtering may remain where applicable, but the obsolete `Clear / All Dates` action is not part of the shared controls.
- The effective pipeline is source/lifecycle scope, filters and search, deterministic sort, export dataset, then screen pagination.
- CSV export includes **all** records in the current effective filtered/searched/sorted view, never only the visible page. Page number, page size, and page-size preferences do not change export membership.
- Export follows effective visible business/data columns in their current order. Hidden columns and `Actions` are excluded. Indicators/statuses export meaningful text, not SVG/React markup.
- Business IDs export as text. Rich text is converted to safe readable text. Commas, quotes, line breaks, empty values, and UTF-8 are handled by the shared CSV utility.

## F. Responsive and zoom behavior

- Browser zoom or a narrow effective viewport must not reorganize approved business field/control placement, row/column relationships, field order, or section structure.
- Shared workspace, form, dashboard, and table containers own scrolling/overflow so approved layouts remain stable.
- Do not globally disable wrapping: wrapping that is intentional *inside* a control or explicitly approved group remains valid. The prohibition is against changing business layout semantics merely because width is reduced.

## G. Save and edit behavior

- Tenant Application Configuration uses the shared metadata-defined configuration field order and controls. It is contour-free/read-only in Tenant view mode, editable in Tenant edit mode, and commits through the Tenant domain/store save boundary; pick-list, multiselect, integer, numeric, and text semantics are never inferred by page heuristics.
- A field that fails validation uses the shared invalid-field presentation and receives the standard red contour without replacing the existing validation message. Pages must not implement object-specific validation styling.
- Save/Apply is the commit boundary where the workflow defines one; draft UI state is not an alternate source of truth.
- After save, records return to their approved non-editing/read-only presentation where applicable. A subsequent Edit action starts a new draft from committed data.
- Where Inline Edit and Advanced Edit are both supported, both remain available. Starting Inline Edit must not remove Advanced Edit; closing Advanced Edit must not remove either option.
- Inline and Advanced paths that perform the same business mutation must share the authoritative transaction rather than drift into separate persistence semantics.

## H. Recurring Infrastructure Maintenance Tasks

### Identity and ownership

- `recurrenceSeriesId` is authoritative series membership; `recurrenceOccurrenceDate` identifies an occurrence within that series; `recurrenceDefinitionTaskId` identifies the authoritative definition task.
- `recurrenceOverrideFields` records field-specific occurrence exceptions. Membership is never inferred from description, task name, dates alone, or visual similarity.

### Editing

- Inline Edit of a recurring task always means **Edit this task**: it updates only the selected occurrence through the shared occurrence transaction and never prompts for series scope.
- Advanced Edit on a recurring task prompts **Edit this task** / **Edit entire series** before the editor opens. Non-recurring tasks open directly.
- In Edit this task, recurrence pattern and range remain visible but completely disabled/read-only and are excluded from editable recurrence validation.
- Occurrence edits preserve series identity and continuation. They do not detach the occurrence, create a new series, truncate the series, or change recurrence.
- Entire-series edits use the domain series transaction. A changed shared field supersedes that same occurrence override only; unrelated occurrence overrides and their metadata remain.
- Recurrence schedule changes reconcile surviving occurrences by authoritative occurrence identity and preserve applicable unrelated exceptions.

### Generation, lifecycle, and presentation

- Newly generated occurrences always start with Task Status `Open` and no completion date, regardless of definition/latest/selected occurrence status.
- Matched existing occurrences retain their status unless Task Status was explicitly changed by the approved entire-series edit. Existing IDs, history, dates, and applicable exceptions remain.
- The shared recurrence indicator is non-clickable. A recurring task shows the repeat indicator; a Done recurring occurrence shows the same indicator crossed through with accessible text `Recurring task – Done`; a non-recurring task shows none.
- Cancelling recurrence is an entire-series operation. It disables future generation, retains original `Done` and `In Progress` records with identity/history/exceptions intact, and removes other generated series occurrences.
- Retained cancelled-series tasks preserve historical `recurrenceSeriesId` membership. Done retains the crossed indicator; In Progress retains the normal indicator.
- Maintenance Tasks remain one complete history list across statuses. The default sort is the raw Start Date descending; user-selected sorting may override it for the current session/view. Search, pagination, and CSV use the effective sorted set.

## I. Infrastructure lifecycle

- Infrastructure workspace tabs are exactly `All Items | Maintenance Tasks`.
- Infrastructure has no user-facing Delete action and no Deleted Items dashboard/saved-view scope.
- `Obsolete` remains a valid Infrastructure operational status and does not imply deletion.
- Legacy persisted Infrastructure records that carry historical deletion metadata must not be physically destroyed by UI cleanup; their data remains available through the current item collection/form presentation.
- Do not reintroduce the superseded Infrastructure Delete/Restore workflow without an explicit new product decision.

## J. Reused Internal Systems

- MID follows the identity rule in section A.
- Purpose derives Availability Status through the owning System Inventory service: `Available` → `Available`; `OBSOLETE` → `Obsolete`; other operational purposes → `Occupied`, subject to authoritative active-allocation precedence.
- Active POC allocation owns POC/Occupied state. POC occupation dates derive from the linked POC Project dates.
- Occupation dates are relevant/editable/required only for an Occupied effective status; non-Occupied states keep those controls inactive/non-required according to the shared form rule.
- Obsolete is a retained business state, not destructive eligibility. Reused Internal Systems cannot be permanently deleted and expose no Permanent Delete action or transaction.

## K. Time Group Settings

- Time Group derivation is owned by the Time Group domain/reference mapping and consumed by dependent Business Objects; pages do not reproduce derivation.
- Wherever Time Group is modeled, Time Zone is the lookup key and the active Time Group Settings row's Time Group Name is the returned value. Country/State-driven Time Zone changes consequently recalculate Time Group. The derived value is not independently editable or allowed to retain a stale fallback when no active mapping matches.
- Time Zone, Country, and State assignments are globally exclusive across active mapping rows.
- Each exclusive selector shows the full valid option universe. Values owned by another active row remain visible but disabled/greyed; values owned by the current row remain enabled/current; unassigned values remain enabled.
- The three selectors share the same ownership/option-state logic and shared selector presentation.
- Time Group Settings uses the shared pageable/history table, including search, Records per page/defaults, counts, navigation, sorting, and CSV. It has no divergent local pagination implementation.

## L. Activity and history

- Correlation ID may remain structured internal Activity metadata, but it is not a user-facing Activity Log column.
- Activity, configuration history, and equivalent history tables use shared read-only, pagination, date/time, Business ID, search, sort, and export behavior.
- Deletion/history presentation exists only for Business Objects whose current approved lifecycle supports it. Project Delete/Restore remains recoverable, retains the PID and business history, and uses the shared deletion-history presentation.
- A recoverable Deleted state does not imply Permanent Delete. Irreversible deletion exists only where an explicit approved domain requirement allows it.

## M. Domain ownership and execution method

- System Number of Tenants is derived once from the complete authoritative active System↔Tenant relationship across Not Set Yet, Under Contract, and Out of Contract. Every presentation consumes that read model; pagination, search, filters, and movement between contract-status views never alter the count.

- Business behavior belongs to Business Objects, domain services, authoritative read models, and store transactions. React pages/components own input, composition, and rendering—not alternate business truth.
- Derived values have one owner. Consumers do not copy derivation or synchronize shadow state.
- Equivalent generic behavior belongs in shared infrastructure (`DataDashboard`, `RecordHistorySection`, Business ID/reference presenters, workspace primitives, shared selectors, status presenters, and similar owners).
- Perform an impact/completeness scan before every fix: inspect current implementation and history, identify the owner and reference pattern, enumerate equivalent usages, and check upstream/downstream save, reload, history, export, navigation, and lifecycle effects.
- Verify interacting workflows at runtime where possible and run the normal build plus targeted checks. Report environment limitations separately; do not claim unperformed verification.
