# Delivery ERP V1.2 standing product rules

## Purpose and authority

This document records the **current approved cross-application V1.2 behavior**. It is an invariant catalog, not a defect or decision history. Apply it together with the [Architecture Handbook](architecture-handbook.md), which remains authoritative for architecture, ownership, and implementation methodology. More-specific Business Object specifications remain authoritative within their stated scope, but must not silently override a generic invariant.

If a requested change conflicts with this document, stop and report the conflict before implementation.

## A. Business identity and navigation

- **Any displayed Business/Object ID must use the shared navigable Business ID/reference presenter whenever a valid target object and supported route exist.** This applies to forms, headers, dashboards, tables, history and configuration history, relationship summaries, candidate dialogs, and read-only presentations.
- Use `BusinessObjectLink`, `BusinessIdLink`, and the Business Reference Resolver. Do not reproduce routing or fallback behavior locally.
- Empty IDs, technical keys, invalid/stale references, and historical snapshots without a valid target use the shared safe fallback rather than a broken link.
- Export and persistence retain plain business-ID text; React link markup never becomes domain data.
- Application-owned Business IDs are generated by the application and are not user-entered fields. This includes Opportunity ID, PID, SID, TID, Requirement ID, Infrastructure Item ID, Maintenance Task ID, Warranty/history IDs, and equivalent ERP-owned identifiers.
- Application-owned Business IDs are unique within their application-wide namespace and are allocated at the approved Save/commit boundary. Create forms may show a read-only application-generated preview ID when that is the established UI behavior, but previewing must not persist the object, reserve the ID permanently, advance counters, create Activity, or change dashboard counts. Opening `New`, cancelling, navigating away, filtering dashboards, deleting, cancelling, releasing, or retaining history never makes a previously used Business ID available for a new record unless an explicit object-specific rule says so.
- Reused Internal System MID input is digits only. Users do not enter the `M`; display is `M<digits>`. A blank MID remains blank and is not generated merely for display.
- MID is the only current manually supplied Business ID. The application must validate MID uniqueness across the reused-internal-system namespace and must not auto-generate MID.

## B. Shared and equivalent UI behavior

- Equivalent behavior must use the approved shared implementation and appear and behave identically across Business Objects.
- This includes workspace navigation, Product sub-tabs, dashboard controls, pagination, Business ID links, selectors, action controls, status/indicator presentation, deletion/history presentation where approved, and read-only fields.
- Do not create an object-specific visual approximation when a shared pattern exists. Extend the shared pattern safely when a genuinely generic capability is missing.

## C. Read-only presentation

- Read-only and system-derived values use the shared contour-free read-only presentation.
- Do not display a non-editable value as a disabled editable control unless the control has an approved inactive-state purpose (for example, showing the locked recurrence definition during occurrence editing).
- View mode must not expose accidental editing affordances. Domain/store commit boundaries must enforce the same effective editability as the UI.

## D. Controlled dashboard columns

- `Update/New` is the first/leftmost permanent framework column. `Actions` is the second. Both remain visible during horizontal scrolling and cannot be hidden, moved, grouped, exported, or saved as business data.
- `Update/New` and `Actions` are the only permanently fixed framework columns. They have no column menu or Freeze indicator and never participate in `Freeze Through`.
- `Creation Date` is an ordinary business column: it does not define where column management or `Freeze Through` begins. Object-specific approved order governs its default position; on the Tenant Dashboard it is last.
- `Freeze Through` choices begin with eligible visible business columns after the permanent framework columns and expose the next five effective visible columns.
- Freeze choices derive dynamically from the effective saved-view column order. The shared `DataDashboard` owns frozen positioning and boundary behavior.
- Grouping never repositions the grouped business column. The column remains in configured order and shows the grouping indicator in its own header.
- The Project Dashboard table frame is the approved shared reference: the frame owns vertical record scrolling, the header remains continuously visible, horizontal header/body scrolling stays aligned, and equivalent dashboards reuse the same constrained dashboard-content structure.

## E. Pagination, search, filters, and CSV

- Paginated dashboards and history/form tables use the common `DataDashboard` or `RecordHistorySection` behavior. Equivalent pagination must not be reimplemented per page.
- Records-per-page choices are `10`, `20`, `25`, `50`, `100`, and `All`; the system default is 10 unless an approved logical table default applies. User defaults belong to presentation preferences, not Business Objects.
- Search/Filter updates results immediately. When text is present, the shared inline `×` clears the complete query and resets pagination; it is absent when the query is empty.
- Date filtering may remain where applicable, but the obsolete `Clear / All Dates` action is not part of the shared controls.
- The effective pipeline is source/lifecycle scope, filters and search, deterministic sort, export dataset, then screen pagination.
- CSV export includes **all** records in the current effective filtered/searched/sorted view, never only the visible page. Page number, page size, and page-size preferences do not change export membership.
- Export follows effective visible business/data columns in their current order. Hidden columns and `Actions` are excluded. Indicators/statuses export meaningful text, not SVG/React markup.
- Business IDs export as text. Rich text is converted to safe readable text. Commas, quotes, line breaks, empty values, and UTF-8 are handled by the shared CSV utility.

## F. Responsive and zoom behavior

- Browser zoom or a narrow effective viewport must not reorganize approved business field/control placement, row/column relationships, field order, or section structure.
- Shared workspace, form, dashboard, and table containers own scrolling/overflow so approved layouts remain stable.
- Do not globally disable wrapping: wrapping that is intentional *inside* a control or explicitly approved group remains valid. The prohibition is against changing business layout semantics merely because width is reduced.

## G. Save and edit behavior

- Tenant Application Configuration uses the same authoritative Product-to-final-column metadata structure as Opportunity New Tenant Requirements from `Product` onward, System Tenant tables, and System Application Configuration Summary. Field IDs/metadata keys, order, labels, field types, option metadata, validation metadata, and product-dependent applicability rules must be defined once in the shared Application Configuration domain and consumed by all four presentations. Tenant remains contour-free/read-only in view mode, editable in edit mode, and commits through the Tenant domain/store save boundary; pick-list, multiselect, integer, numeric, and text semantics are never inferred by page heuristics.
- Standard dashboard `New` actions open a new/create form with unsaved draft state only. They must not call persisted `create*` store transactions, allocate/commit business IDs, create Activity, or change dashboard counts merely to obtain a route or default object. Object creation, business-ID counter advancement, Activity creation, and persistence occur only at the approved Save boundary. Closing, cancelling, or navigating away from an unsaved create form leaves no persisted object and consumes no business ID, including no permanent local reservation of an application-owned ID.
- A field that fails validation uses the shared invalid-field presentation and receives the standard red contour without replacing the existing validation message. Pages must not implement object-specific validation styling.
- Save/Apply is the commit boundary where the workflow defines one; draft UI state is not an alternate source of truth.
- After save, records return to their approved non-editing/read-only presentation where applicable. A subsequent Edit action starts a new draft from committed data.
- Where Inline Edit and Advanced Edit are both supported, both remain available. Starting Inline Edit must not remove Advanced Edit; closing Advanced Edit must not remove either option.
- Inline and Advanced paths that perform the same business mutation must share the authoritative transaction rather than drift into separate persistence semantics.

## H. Recurring Infrastructure Maintenance Tasks

### Identity and ownership

- `recurrenceSeriesId` is authoritative series membership; `recurrenceOccurrenceDate` identifies an occurrence within that series; `recurrenceDefinitionTaskId` identifies the authoritative definition task.
- `recurrenceOverrideFields` records field-specific occurrence exceptions. Membership is never inferred from description, task name, dates alone, or visual similarity.

### Editing

- Inline Edit of a recurring task always means **Edit this task**: it updates only the selected occurrence through the shared occurrence transaction and never prompts for series scope.
- Advanced Edit on a recurring task prompts **Edit this task** / **Edit entire series** before the editor opens. Non-recurring tasks open directly.
- In Edit this task, recurrence pattern and range remain visible but completely disabled/read-only and are excluded from editable recurrence validation.
- Occurrence edits preserve series identity and continuation. They do not detach the occurrence, create a new series, truncate the series, or change recurrence.
- Entire-series edits use the domain series transaction. A changed shared field supersedes that same occurrence override only; unrelated occurrence overrides and their metadata remain.
- Recurrence schedule changes reconcile surviving occurrences by authoritative occurrence identity and preserve applicable unrelated exceptions.

### Generation, lifecycle, and presentation

- Newly generated occurrences always start with Task Status `Open` and no completion date, regardless of definition/latest/selected occurrence status.
- Matched existing occurrences retain their status unless Task Status was explicitly changed by the approved entire-series edit. Existing IDs, history, dates, and applicable exceptions remain.
- The shared recurrence indicator is non-clickable. A recurring task shows the repeat indicator; a Done recurring occurrence shows the same indicator crossed through with accessible text `Recurring task – Done`; a non-recurring task shows none.
- Cancelling recurrence is an entire-series operation. It disables future generation, retains original `Done` and `In Progress` records with identity/history/exceptions intact, and removes other generated series occurrences.
- Retained cancelled-series tasks preserve historical `recurrenceSeriesId` membership. Done retains the crossed indicator; In Progress retains the normal indicator.
- Maintenance Tasks remain one complete history list across statuses. The default sort is the raw Start Date descending; user-selected sorting may override it for the current session/view. Search, pagination, and CSV use the effective sorted set.

## I. Infrastructure lifecycle

- Infrastructure workspace tabs are exactly `Active Items | Maintenance Tasks | Cancelled Infrastructure Items`.
- Infrastructure has no user-facing Delete action and no Deleted Items dashboard/saved-view scope.
- `Obsolete` remains a valid Infrastructure operational status and does not imply deletion.
- Legacy persisted Infrastructure records that carry historical deletion metadata must not be physically destroyed by UI cleanup; their data remains available through the current item collection/form presentation.
- Do not reintroduce the superseded Infrastructure Delete/Restore workflow without an explicit new product decision.

## J. Reused Internal Systems

- MID identifies the reusable internal System/resource itself. MID is fixed for that resource, is manually supplied/validated, and may appear across multiple historical or current Project allocation uses.
- SID identifies an allocated System instance. Every System allocated to a Project has its own SID, including allocations originating from a Reused Internal System. Allocating a Reused Internal System retains the MID and generates a new globally sequential SID at the allocation/save boundary.
- Allocated Systems is a SID/allocation-instance view. Do not deduplicate, collapse, or route allocated rows by MID; the same MID may legitimately appear in multiple allocated rows over time while each row has its own SID/PID.
- Reused Internal Systems is a MID/resource inventory view. It includes every non-Cancelled Reused Internal System regardless of Availability Status, Operational Status, current occupation, or prior POC usage.
- Purpose derives Availability Status through the owning System Inventory service: `Available` → `Available`; `OBSOLETE` → `Obsolete`; other operational purposes → `Occupied`, subject to authoritative active-allocation precedence.
- Active POC allocation owns POC/Occupied state. POC occupation dates derive from the linked POC Project dates.
- Occupation dates are relevant/editable/required only for an Occupied effective status; non-Occupied states keep those controls inactive/non-required according to the shared form rule.
- Obsolete is a retained business state, not destructive eligibility. Reused Internal Systems cannot be permanently deleted and expose no Permanent Delete action or transaction.

## K. Time Group Settings

- Time Group derivation is owned by the Time Group domain/reference mapping and consumed by dependent Business Objects; pages do not reproduce derivation.
- Wherever Time Group is modeled, Time Zone is the lookup key and the active Time Group Settings row's Time Group Name is the returned value. Country/State-driven Time Zone changes consequently recalculate Time Group. The derived value is not independently editable or allowed to retain a stale fallback when no active mapping matches.
- Time Zone, Country, and State assignments are globally exclusive across active mapping rows.
- Each exclusive selector shows the full valid option universe. Values owned by another active row remain visible but disabled/greyed; values owned by the current row remain enabled/current; unassigned values remain enabled.
- The three selectors share the same ownership/option-state logic and shared selector presentation.
- Time Group Settings uses the shared pageable/history table, including search, Records per page/defaults, counts, navigation, sorting, and CSV. It has no divergent local pagination implementation.

### Geography ownership and System hosting governance

- Customer geography is the business origin. Opportunity, Project, and Tenant geography propagates from that Customer context; Project and Tenant geography is not independently editable in V1.2.
- Country/State derives Time Zone, and Time Zone resolves through the active Time Group Settings row to Time Group Name. No Time Zone means no Time Group. Region and stale persisted values are never Time Group fallbacks.
- Project Time Group is geography-derived from its Opportunity/Customer context. Tenant Time Group is geography-derived from its Project/Customer context. The veteran-Tenant rule does not apply to Projects or Tenants.
- System Time Group represents the external Customer/POC working-hours context used for maintenance scheduling. Only active Customer and POC Tenants are eligible governors when a System has active hosted Customer/POC Tenants; Internal Tenants never establish, replace, or govern it and never trigger the mismatch workflow. A standalone inventory System with no active eligible hosted Tenant may display its own inventory/location Time Group.
- An additional Tenant with a different Time Group pauses before mutation and offers exactly **Continue**, **Cancel**, and **Change**. Continue atomically adds the Tenant while preserving System governance; Cancel performs no mutation; Change atomically adds the Tenant and replaces System Time Group governance with the incoming Tenant. Neither Continue nor Change modifies Tenant geography.
- A valid active explicit Customer/POC governor selected by **Change** has precedence. Otherwise, the most veteran active Customer/POC Tenant governs. When the governor leaves active hosting, the same selection is re-evaluated; when no active eligible Tenant remains, tenant-derived System Time Group is empty and a tenant-less standalone inventory System falls back only to its own inventory/location Time Group. Project and Region are never fallbacks.
- The System Tenant tab shows a compact globe beside the governing Tenant's visible Time Group in each applicable contract-status table. The globe is driven by the authoritative System Time Group source read model and means `System Time Group source`; Internal and non-governing Tenants never show it.
- System Number of Tenants always uses the complete authoritative active hosting relationship.
- Tenant Configuration is the Tenant-owned editable configuration. System Tenant tables show read-only individual Tenant configuration values, and System Application Configuration Summary is a separate, read-only aggregation of active hosted Tenant configurations. All configuration presentations derive their Product-to-final-column structure from the same shared Application Configuration metadata, while every summary presentation uses the same System read model.
- Individually Deleted Tenants and retained legacy Cancelled Tenant records remain historically linked to their hosting System and to any current Project attachment that still exists. Deleted Tenants are excluded from active System counts and System Application Configuration Summary, and the System form presents them in a dedicated retained `Deleted Tenants` table below the active Application Configuration Summary with Warranty Status and without operational Actions. Retained legacy Cancelled Tenants are excluded from normal operational collections, including Tenant Dashboard, Project Tenant tables, System Tenant tables, selectors, and active counts/summaries, while remaining available to explicit history/audit/provenance views. Warranty Status remains a column/filter/grouping value for operational and retained Deleted Tenant rows and never determines Tenant Workspace membership.
- System-forced Tenant statuses are separate from individual Delete. When a hosting System is set to `Off`, `Access blocked`, or `Service blocked`, only currently hosted Tenants that were not already individually Deleted or legacy Cancelled are temporarily forced to the corresponding Tenant status. The Tenant stores the exact previous Operational Status and the forcing System. Returning the System to `On` restores only those system-forced Tenants and does not restore individually Deleted or legacy Cancelled Tenants. Dedicated System cancellation from the System form header is not a shortcut for deallocation or occupation release: an allocated Production System cannot be cancelled until all active Project allocations are manually deallocated through the Project workflow, and an occupied Reused Internal System cannot be cancelled until released through its normal operational workflow. Only an unallocated Production System or available/unoccupied Reused Internal System may be cancelled. Restore returns the System itself to inventory/available state and never reconstructs Project allocation or occupation.
- Tenant manual Operational Status choices are limited to `Active` and `Access Blocked - Password Reset`. System-derived/forced values are read-only and must not be manually selectable.

## L. Activity and history

- Correlation ID may remain structured internal Activity metadata, but it is not a user-facing Activity Log column.
- Activity, configuration history, and equivalent history tables use shared read-only, pagination, date/time, Business ID, search, sort, and export behavior.
- Deletion/cancellation/history presentation exists only for Business Objects whose current approved lifecycle supports it. Project cancellation remains recoverable, retains the PID and business history, and uses the shared history presentation. Project dashboard deletion is not an approved V1.2 action.
- Project, System, and Infrastructure Item cancellation controls are presented on a dedicated final header row after normal business header fields. Cancellation Reason uses the shared rich-text editor and shared rich-text read-only renderer; the row shows `Cancel <Object>`, `Cancellation Timestamp`, `Cancelled By`, and `Cancellation Reason` when cancellation is requested or committed. Cancellation must be blocked at the store/domain boundary while release-first relationships still exist: Projects with active System allocations, Systems with active Project allocations, occupied Reused Internal Systems, and Infrastructure Items linked to Systems.
- When Project, System, or Infrastructure cancellation validation fails, both the `Cancel <Object>` Yes/No control and the Cancellation Reason editor use the shared invalid-field contour. Blocking requirement messages use error presentation; success messages remain green; informational/non-blocking messages remain informational.
- Cancelled Project, System, Infrastructure, and retained legacy Cancelled Tenant records are historical/audit records. Normal operational dashboards, embedded relationship tables, selectors, allocation/attach dialogs, active summaries, and operational lookup sources exclude Cancelled records unless a view is explicitly a dedicated Cancelled/history/audit/provenance presentation. Filtering Cancelled records from operational read models must not physically delete records or erase SID/PID/MID/TID relationship history.
- A recoverable Deleted state does not imply Permanent Delete. Irreversible deletion exists only where an explicit approved domain requirement allows it.

## M. Tenant type and warranty relevance

- Tenant Type is determined at creation by the authoritative Project-to-Tenant mapping or explicit Internal Tenant creation flow and remains read-only in the Tenant form. The sole post-creation exception is the workflow-controlled conversion of an eligible surviving POC Tenant hosted on a Production System to Customer when it is selected as an existing-Tenant Change Request and an approved Delivery-Upsell or Renewal-Upsell is fulfilled. The transaction preserves POC history, reuses the Tenant and hosting System, adds the Upsell relationships, emits Activity, and only then enables Customer warranty semantics.
- A POC Tenant actively linked to an active POC Project shows read-only POC Start Date and POC End Date in its header, derived from that Project's Start Date and End Date. The derived dates disappear when the qualifying active relationship ends and are not separately persisted on Tenant.
- Tenant header Warranty Status is populated from the authoritative WarrantyCollection read model only for Customer Tenants. It is visually empty for every non-Customer Tenant.
- The Tenant Warranty section is relevant for a Customer Tenant with Tenant-owned Delivery or Renewal Project context, including the retained Origin PID/Project, Requirement history, current ProjectTenant membership, or existing Warranty records. The section must not disappear merely because there is no current Warranty row, the Project is completed/deallocated, or the Tenant is Deleted. Retained legacy Cancelled Tenants may remain inspectable through explicit historical/audit access, but do not participate in normal operational Tenant collections. Add/Edit manageability may still be restricted when required Project/Opportunity context cannot be resolved. POC, Internal, and other non-Customer Tenants do not qualify.
- Tenant cancellation is no longer an active Tenant lifecycle workflow. The application must not expose a Tenant `Cancel` action or Tenant `Restore` action. Retained legacy Cancelled Tenant records remain visible historically with their existing cancellation audit fields where present.

## N. Domain ownership and execution method

- System Number of Tenants is derived once from the complete authoritative active System↔Tenant relationship across Not Set Yet, Under Contract, and Out of Contract. Every presentation consumes that read model; pagination, search, filters, and movement between contract-status views never alter the count.

- Business behavior belongs to Business Objects, domain services, authoritative read models, and store transactions. React pages/components own input, composition, and rendering—not alternate business truth.
- Derived values have one owner. Consumers do not copy derivation or synchronize shadow state.
- Equivalent generic behavior belongs in shared infrastructure (`DataDashboard`, `RecordHistorySection`, Business ID/reference presenters, workspace primitives, shared selectors, status presenters, and similar owners).
- Dashboard search/filter/grouping behavior is shared in `DataDashboard`. Filters use the dashboard column contract and split semicolon-delimited multi-value cells into independently selectable/searchable values. When a dashboard is grouped, sorting another column sorts rows within each group without flattening records across group boundaries.

## M. Tenant Dashboard relationship context

- The Tenant Dashboard has separate `Origin Project` and `PIDs` relationship columns. `Origin Project` is the selected PID/Project established at Tenant creation and retained for Tenant lifetime/history regardless of Operational Status. `PIDs` is current Project membership only, derived from active ProjectTenant attachments backed by active System allocation; historical PID provenance must not silently repopulate current membership after deallocation.
- `Requirement IDs` displays PID-qualified Requirement relationships (`PID-A-xxx`). Customer and POC Tenants created from Project Tenant Requirements must carry Requirement history that resolves to a Requirement belonging to the same PID/Project. Internal Tenants may legitimately have a PID relationship without a Requirement ID.
- Requirement IDs are globally unique across all Opportunity and Project Tenant Requirement grids and all retained Tenant Requirement identity/history references, and are generated from one application-wide human-readable sequence (`A-001`, `A-002`, `A-003`, ...). Random/hash suffixes are invalid. A Project Tenant Requirement may be associated with more than one Tenant; Requirement pickers must not disable a Requirement merely because another Tenant already references it. Released/historical Requirement relationships remain visible as history. Requirement ID identity is never reused by a newly created Requirement.
- Multi-value cells use semicolon-delimited display with no added arbitrary whitespace: `<item 1>;<item 2>;<item 3>`.
- `Project Type` and `Project Sub Type` appear immediately after Tenant Type and describe the Project in which the Tenant was originally created. Later Project participation does not overwrite those originating Project values.
- Account Name and Region remain single values from the Tenant's authoritative Customer/Account geography context.
- The default Tenant business-column order is TID, SID, Origin Project, PIDs, Tenant Type, Project Type, Project Sub Type, Account Name, Region, Operational Status, Warranty Status, Requirement IDs, Product, System URL, System Version, Hosting, Platform; all existing configuration fields from Number of Users through Additional Sources in approved relative order; Warranty Initial Date, Warranty Start Date, Warranty End Date, POC Start Date, POC End Date, Update Date, Creation Date. Creation Date is last.
- Perform an impact/completeness scan before every fix: inspect current implementation and history, identify the owner and reference pattern, enumerate equivalent usages, and check upstream/downstream save, reload, history, export, navigation, and lifecycle effects.
- Verify interacting workflows at runtime where possible and run the normal build plus targeted checks. Report environment limitations separately; do not claim unperformed verification.

## O. Project template and historical relationship rules

- Standard Project milestone/task templates are the nine workbook-defined templates from `Projects - SF design 19-08-26.xlsx`, sheet `Milestones and Tasks Template`.
- Project template resolution is governed by the first lookup table in workbook sheet `Project form - general`. POC supports Grid A only, Grid B only, and Grid A plus Grid B. POC A-only and A+B use Template #1; POC B-only uses Template #2.
- Tenant creation retains historical Origin Project/PID provenance, but current Project Systems/Tenants membership is governed by active System allocation plus active Tenant Requirement attachment. Tenant Workspace has one operational Tenant Dashboard containing non-Cancelled Tenants; retained legacy Cancelled Tenants remain historical/audit data only. Warranty Status remains independent business data and must not be rewritten or used as a workspace partition. Operational Status is shown inside Tenant rows and does not create Project membership by itself. System deallocation releases current Project membership without deleting Tenant/System/Requirement history and must not be silently reversed by PID history.
- Moving a Tenant changes the Tenant's current active hosted System relationship for active work, but must not rewrite completed/historical Project-System-Tenant relationship snapshots.
- A successful POC Tenant hosted on a customer Production System may be selected as an existing-Tenant Change Request in Delivery-Upsell or Renewal-Upsell. Fulfillment reuses the Tenant and hosting System, converts Tenant Type to Customer, sets Warranty Status to `Not Set Yet`, adds the Upsell Project/Requirement relationships, and preserves the original POC Project history.
- System existence and Project allocation are separate. Production Systems and Reused Internal Systems may exist with no Tenant, no Project allocation, or neither; standalone inventory Systems are valid and must not be auto-allocated. When a System is allocated, the allocation must point to a valid POC, Delivery, or Renewal Project. System deallocation is an explicit Project workflow and returns Production Systems to inventory availability according to existing inventory rules; Reused Internal System allocation creates a distinct allocated SID instance while preserving the reusable MID resource identity. Allocated Systems cannot be changed to `Cancelled` or `Deleted` from the System form; users must manually deallocate all Project allocations first. Tenant invariants remain stricter: every active Tenant must resolve its current hosting System; active POC or Customer Tenants attached to a Project must resolve the same-Project Tenant Requirement.
- Manual Tenant Move between Systems is obsolete. Continuing a Tenant on another System is modeled by terminating the old Tenant according to lifecycle rules and creating a new Tenant on the destination System, with predecessor linkage through Warranty where applicable.
- Tenant Warranty Related Project ID is Tenant-driven. It may include the Tenant creation PID and other Tenant-specific Project relationships such as Renewal/Upsell, but must not include a Project solely because the hosting System is allocated or linked to that Project.
- Opportunity Requirement rows participate operationally only when their grid is currently applicable to the Opportunity's active Type/Subtype/Stage/workflow configuration. Stored rows from a previous configuration may be retained for history or state restoration, but hidden/non-applicable rows must not drive active validation, Project generation, System auto-allocation, Tenant creation, Requirement Coverage, operational summaries, selectors, or read models.
- Opportunity Customer Existing Tenants / Systems is Tenant-driven. It lists eligible Customer Tenants for the Opportunity Account with warranty header status `Under Contract` or `Not Set Yet`; it excludes POC Tenants, Internal Tenants, ineligible Customer Tenants, and all system-only rows. Grid B/C use the same eligible Customer Tenant set. Grid A existing-System options are derived only from Systems currently hosting eligible Customer Tenants, grouped by current Account first and other same Sales Manager / Deal Owner Accounts second.
- There is no Tenant Name business field. Tenant UI, read models, exports, links, and documentation must use TID plus authoritative Account/System/Project/Requirement context instead of storing or displaying a separate Tenant Name.
