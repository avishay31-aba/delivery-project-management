# Systems Workspace Product Design Specification

## 1. Workspace Purpose

Systems Workspace is the Delivery-owned workspace for the System Business Object.

It provides the operational environment for viewing and managing allocated systems, production inventory systems, and reused internal systems as views of the same System Business Object.

## 2. Business Ownership

System is Delivery-owned.

SystemInventory owns System identity, operational status, infrastructure configuration, hosting context, Application Configuration Summary, System Configuration History, and System-owned read models.

AllocationContext owns project-system allocation semantics.

TenantOperations owns tenant lifecycle and tenant operational facts.

Systems Workspace composes these facts without transferring ownership.

## 3. Version 1.0 Workspace Structure

Systems Workspace uses tabs/views for:

- Allocated Systems
- Production Inventory
- Reused Internal Systems

These are views of System, not separate Business Objects or separate sidebar workspaces.

Existing approved System form layout, spacing, field placement, table density, and workflow are product assets and must be preserved unless explicitly changed by the Product Owner.

## 4. Form Mode Behavior

Systems Workspace forms should support:

- View mode
- Edit mode

View mode presents System facts read-only, without editable borders/contours.

Edit mode enables approved editable fields and actions.

Mandatory fields show a red asterisk next to the field label.

Read-only fields render as plain values without input styling.

## 5. Header And Toolbar

The header should preserve the approved System form appearance.

Toolbar actions should be V1-safe and should not introduce new workflows.

Dashboard/list navigation into the System form should use:

- Eye action for View mode
- Pencil action for Edit mode

Rows themselves should not be the primary navigation control.

## 6. Existing Tabs And Sections

Existing tabs and sections remain approved product assets.

Application Configuration Summary remains System-owned and should continue to use the existing configuration column structure and terminology.

Hosted Tenants remain displayed as System context, while Tenant lifecycle stays owned by TenantOperations.

Purpose History for reused internal systems remains System context and must preserve historical allocation visibility.

## 7. Remarks Section

Systems Workspace should add a Remarks section beneath the existing tabs.

Remarks are reusable child Business Objects. They may later be reused under System, Project, Tenant, Opportunity, Customer, Warranty, or other approved parent objects. In V1 they may be implemented first under System.

Remarks section behavior:

- Editable grid.
- Uses generated unique IDs.
- Uses full timestamp.
- Uses current user/author metadata on creation.
- Preserves original author metadata when later edited, where supported.
- May track last modified by / last modified timestamp where supported.
- Uses shared RichTextEditor for content.
- Uses shared deadline alert presentation for due-date alert output.

Columns:

1. Actions: edit, delete
2. Unique ID: read-only, autogenerated
3. Full timestamp: read-only, autogenerated
4. User name / author: read-only, autogenerated
5. Type: editable single-select picklist
6. Content: editable rich text
7. Due date: editable date
8. DL alert: read-only autogenerated

Approved type values:

- Note
- Task
- Temporary change
- Permanent change/task
- Add new...

Remark author metadata is not the Owner table.

## 8. Configuration History Section

Systems Workspace should add a Configuration History section beneath the existing tabs.

Configuration History is System-owned business history.

It is not generic.

It is not Activity Log.

It records System Application Configuration Summary snapshots/history when the System-owned configuration changes as a result of approved tenant/system configuration flows.

Configuration History behavior:

- Read-only table.
- Generated unique ID.
- Full timestamp.
- User name for the user who caused the System Application Configuration Summary to change, where user context exists.
- From column 4 onward, the same columns/structure as Application Configuration Summary.

Columns:

1. Unique ID: read-only, autogenerated
2. Full timestamp: read-only, autogenerated
3. User name
4. Application Configuration Summary columns

Activity Log may record that a configuration event happened. Configuration History preserves the business configuration snapshot.

## 9. Owner Tab

Systems Workspace should add a final tab called Owner.

Owner / Responsible Contact is a reusable child Business Object/table. It may later be reused under System, Project, Tenant, Customer, or other approved parent objects. In V1 it may be implemented first under System.

Owner tab behavior:

- Editable table.
- Represents responsible people/contacts for the System.
- Does not define ERP roles or privileges.
- Does not replace Remark author metadata.

Columns:

1. User ID
2. User name
3. Full name
4. Title
5. Company
6. Phone number
7. Email

## 10. System Creation Rules

For both Production System and Reused Internal System:

- Used In Region must be mandatory where the field exists.
- Used In Region must be empty by default on creation.
- The user must explicitly select Used In Region.
- New system creation must not auto-fill Used In Region.

Existing validation style/messages should be reused.

## 11. Business Rules

- System remains Delivery-owned.
- System owns Application Configuration Summary.
- Configuration History remains System-owned.
- Tenant lifecycle remains TenantOperations-owned.
- Allocation lifecycle remains AllocationContext-owned.
- Remarks and Owner rows are child structures under their parent object and do not transfer ownership.
- Pages render and coordinate; they must not own business rules.

## 12. Version 2.0 Exclusions

Do not include in V1:

- Configurable System workspace layouts.
- Configurable child-object designer.
- Generic cross-object Remarks rollout beyond approved parent objects.
- Generic cross-object Owner rollout beyond approved parent objects.
- Generic Configuration History framework outside System.
- Configurable workflow designer.
- Configurable permission designer.
